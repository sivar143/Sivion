# Sivion Technical Information

## 1. Purpose

This document is the developer-facing technical reference for Sivion. It describes the architecture, technology stack, implementation conventions, current modules, infrastructure, integrations, security model, local development environment, and engineering rules used by the project.

The document intentionally separates implementation details from the client/user documentation in `USER_GUIDE.md`.

> **Scope:** This document describes the currently implemented platform and the stabilization direction. It must not be interpreted as a specification that all future modules are already implemented.

## 4. Architectural model

Sivion follows a modular monolithic backend structure with clear domain boundaries and event-driven integration. The current implementation is intentionally structured so that individual business areas can later be extracted into independently deployable services without forcing a rewrite of the business model.

The main layers are:

```text
Angular UI
    ↓
HTTP / REST API
    ↓
Spring services/controllers
    ↓
Domain + repositories
    ↓
MySQL system of record

Cross-module asynchronous integration
    ↕
RabbitMQ

Caching / rate limiting / coordination
    ↕
Valkey

Identity / roles / JWT
    ↕
Keycloak

External web boundary
    ↕
Nginx
```

### Architectural rules

1. MySQL is the authoritative system of record for business data.
2. Cross-module business state must not be synchronized by directly sharing another module's JPA entities or repositories.
3. REST APIs are used for synchronous cross-domain operations where an immediate response is required.
4. RabbitMQ domain/integration events are used for asynchronous workflows.
5. Event consumers must be idempotent because messages may be delivered more than once.
6. Business writes should be transactional.
7. Domain events generated by transactional writes should be published after a successful database commit.
8. Tenant isolation must be preserved at every repository/service boundary.
9. Inventory is treated as a transaction ledger, not as an unrestricted mutable balance.
10. Security decisions belong to authenticated identity, role, permission, and scope rather than UI visibility alone.

## 5. Current implemented business areas

### CRM

Current CRM functionality includes:

- Customers
- Contacts
- Leads
- Opportunities
- Activities
- Customer/lead/opportunity lifecycle APIs
- Tenant-scoped access
- Generated business identifiers
- Validation and duplicate customer protection

Lead lifecycle includes `NEW`, `CONTACTED`, `QUALIFIED`, and `CONVERTED`.

Opportunity stages include `QUALIFICATION`, `NEEDS_ANALYSIS`, `PROPOSAL`, `NEGOTIATION`, `CLOSED_WON`, and `CLOSED_LOST`.

### Sales Orders

Sales orders include customer, optional opportunity, item lines, quantities, unit prices, total amount, delivery address, notes, and status.

The current lifecycle includes:

```text
DRAFT
  ↓
CONFIRMED
  ↓
RESERVED
  ↓
PARTIALLY_DISPATCHED
  ↓
DISPATCHED
```

`RESERVATION_FAILED` is used when inventory cannot satisfy a reservation and can be retried by reconfirming the order or resolved by cancellation.

Cancellation emits `sales.order.cancelled` and inventory releases active reservations.

Inventory can emit `inventory.order.dispatched` with a completion indicator. Partial dispatches therefore remain distinguishable from final dispatch.

### Inventory

Current inventory functionality includes:

- Material/product records
- Warehouses
- Stock-in
- Stock adjustments
- Inventory transaction ledger
- Reservations
- Sales-order dispatch
- Dispatch history
- Available quantity calculation
- Pessimistic locking for critical stock operations
- Deterministic product locking for multi-line operations

Available stock is calculated from ledger balance less active reserved quantity. Reservations themselves do not create a stock transaction; dispatch consumes reservations and creates the corresponding inventory transaction.

### Procurement

Current procurement functionality includes:

- Suppliers
- Purchase requests
- Purchase orders
- Purchase order items
- Goods receipts
- Purchase-order receipt lifecycle
- Inventory integration for received goods

Supplier codes are normalized and duplicate codes are prevented within the tenant.

Goods receipt processing validates that cumulative received quantity does not exceed ordered quantity. Receipt events are integrated with inventory using a business reference so duplicate event delivery can be prevented.

### Finance

Current finance functionality includes:

- Invoices
- Payments
- Expenses
- Invoice/payment status handling
- Sales-order dispatch integration

Payment processing locks the invoice row before checking the cumulative amount, preventing concurrent payment requests from independently exceeding the invoice total.

Final sales-order invoicing is driven by the completed dispatch event rather than a partial dispatch event.

### HR

The application currently contains HR/employee workspace and implementation areas for employees, organization, attendance, leave, holidays, meetings, performance, goals, knowledge development, employee documents, and reports.

HR remains part of the current implementation and stabilization scope. New unrelated business modules should not be introduced while the current stabilization iterations are in progress.

## 7. Tenant isolation

The current backend services use tenant-scoped repository methods and the development environment uses tenant `1` as the default development tenant.

This is a development convenience, not the final production tenant-identification strategy.

Production implementation must derive tenant identity from a trusted authenticated context and must never trust an arbitrary client-supplied tenant identifier as the sole authorization mechanism.

When adding a new entity or repository:

- Include tenant ownership where the record is tenant-specific.
- Add tenant-aware repository queries.
- Include tenant conditions in update/delete/read operations.
- Add uniqueness constraints with tenant columns where the business identifier is tenant-local.
- Add tests proving that one tenant cannot access another tenant's records.

## 8. REST API conventions

The backend uses versioned API paths under:

```text
/api/v1/
```

The API includes actuator health information separately from business APIs.

Validation failures and business lifecycle errors should be translated into appropriate HTTP responses by the centralized API exception handling layer.

Typical semantics are:

- `400` for invalid request data/business input.
- `401` for unauthenticated access.
- `403` for authenticated but unauthorized access.
- `404` for tenant-scoped resources that do not exist.
- `409` for lifecycle conflicts or data conflicts.
- `5xx` for unexpected server failures.

Do not expose stack traces, SQL details, credentials, tokens, or internal implementation details in API error responses.

## 9. Event-driven integration

RabbitMQ uses the durable topic exchange:

```text
sivion.events
```

Current event flows include:

```text
sales.order.confirmed
        ↓
Inventory reservation
        ↓
inventory.order.reserved
        ↓
Sales order → RESERVED
```

Reservation failure:

```text
sales.order.confirmed
        ↓
Inventory reservation fails
        ↓
inventory.order.reservation-failed
        ↓
Sales order → RESERVATION_FAILED
```

Cancellation:

```text
sales.order.cancelled
        ↓
Inventory releases active reservations
```

Dispatch:

```text
Inventory dispatch
        ↓
inventory.order.dispatched
        ├── complete=false → Sales order remains PARTIALLY_DISPATCHED
        └── complete=true  → Sales order becomes DISPATCHED
                              ↓
                         sales.order.dispatched
                              ↓
                         Finance creates invoice
```

Procurement:

```text
procurement.goods-received
        ↓
Inventory stock transaction
```

### Event reliability rules

- Publish transactional domain events after successful database commit.
- Consumers must tolerate duplicate messages.
- External references such as sales order IDs and goods receipt IDs should be used as idempotency keys where appropriate.
- Never assume that a message is delivered exactly once.
- A consumer should not acknowledge a message as successfully processed when a required state change has definitely failed.
- Retry/DLQ policies should be configured before production deployment.

## 10. Inventory consistency rules

Inventory is one of the highest-risk domains for data corruption. Changes must preserve these rules:

1. Do not update a stock balance as a replacement for recording the underlying business transaction.
2. Lock the relevant inventory records before calculating and applying a critical stock change.
3. For multi-line operations, lock records in deterministic order to reduce deadlock risk.
4. Reservations must be included when calculating available stock.
5. A dispatch linked to a sales order must consume the corresponding active reservation.
6. Cancellation must release active reservations.
7. Replayed integration messages must not create duplicate stock transactions.
8. Partial dispatch must not be treated as final fulfillment.
9. Stock quantities must not become negative unless an explicitly designed business rule permits it.

## 11. Finance consistency rules

Payment operations are concurrency-sensitive. The invoice row is locked before calculating outstanding amount so two concurrent payment requests cannot both observe the same stale outstanding balance.

For sales-order invoicing:

- Partial dispatch must not generate the final invoice.
- Final dispatch should generate one invoice for the completed sales order.
- The sales order ID is the business correlation key for the generated invoice.
- Duplicate event delivery must not create duplicate invoices.

Database-level uniqueness should be used as a second line of defense for business keys wherever practical.

## 12. Caching and Valkey

Valkey is accessed through Spring's Redis-compatible data abstractions.

Current usage is intended for:

- Read caching where appropriate.
- Rate limiting/coordination.
- Future distributed coordination needs.

Valkey must not become the authoritative store for financial, inventory, customer, or other business records. Critical business state belongs in MySQL.

## 13. Docker local environment

The main `docker-compose.yml` currently provisions:

| Service | Purpose | Local port |
|---|---|---:|
| MySQL | System of record | 3306 |
| Valkey | Cache/coordination | 6379 |
| RabbitMQ | Async messaging | 5672 / 15672 |
| Keycloak | Identity/RBAC | 8081 |
| Backend | Spring Boot API | 8080 |
| Frontend | Angular + Nginx | 4200 |

Start the stack with:

```bash
docker compose up --build
```

Stop it with:

```bash
docker compose down
```

To remove local database volumes as well:

```bash
docker compose down -v
```

Use the last command only when intentionally resetting local persistent data.

## 15. Configuration and secrets

Development credentials currently exist in Docker Compose for convenience. They must not be reused in production.

Production configuration should provide secrets through the deployment environment or a proper secret-management system rather than committing credentials into source control.

At minimum, production deployments must externalize:

- Database credentials
- Keycloak administrator/bootstrap credentials
- RabbitMQ credentials
- JWT/identity configuration where environment-specific
- TLS certificates/private keys
- Any third-party integration credentials

## 16. Frontend runtime configuration

The Angular application supports runtime configuration for Keycloak values rather than requiring a source-code rebuild for every environment.

The runtime configuration includes:

- Keycloak URL
- Keycloak realm
- Keycloak client ID

Local development defaults point to the local Keycloak instance. Non-local deployments can provide environment-specific configuration through the deployed web boundary.

## 17. Database practices

MySQL is the authoritative relational datastore.

Database changes must:

- Preserve tenant isolation.
- Use appropriate foreign keys and indexes where practical.
- Use business uniqueness constraints where duplicate records would be harmful.
- Consider concurrency when a value is read, validated, and then written.
- Avoid relying exclusively on application-level duplicate checks for race-sensitive business keys.

Schema evolution should be handled deliberately. Local development may use automatic JPA schema evolution where configured, but production database migration should use a controlled migration process rather than relying on automatic destructive schema changes.

## 18. Testing expectations

Every functional change should be accompanied by the appropriate level of automated verification.

Important test categories include:

### Unit/service tests

- Validation
- Lifecycle transitions
- Business calculations
- Tenant isolation
- Idempotency
- Error conditions

### Integration tests

- Repository behavior
- Transaction boundaries
- Locking/concurrency-sensitive operations
- RabbitMQ event consumers
- Cross-module workflows

### Frontend tests/build

- Component behavior
- API client behavior
- Role/workspace visibility
- Error handling
- Production build validation

### End-to-end workflows

Important business scenarios include:

1. Create and confirm a sales order.
2. Reserve available inventory.
3. Handle reservation failure and retry.
4. Cancel an order and release its reservation.
5. Partially dispatch an order.
6. Complete the remaining dispatch.
7. Generate exactly one invoice after final dispatch.
8. Apply concurrent payments without exceeding the invoice amount.
9. Receive procurement goods and update inventory exactly once.

## 19. Current stabilization priority

The current development phase is intentionally focused on hardening existing functionality before introducing additional business modules.

Priority areas are:

1. Sales-order lifecycle consistency.
2. Inventory reservation and dispatch correctness.
3. Event idempotency and failure handling.
4. Finance invoice/payment consistency.
5. Procurement receipt integration.
6. CRM lifecycle validation and tenant safety.
7. HR functionality already present in the repository.
8. Angular state management, error handling, and role/workspace behavior.
9. Docker/configuration consistency.
10. Automated tests and CI reliability.

Do not start new business modules merely to increase the apparent feature count while these areas contain correctness or reliability issues.

## 20. Developer change checklist

Before committing a backend feature:

- [ ] Is the operation tenant-scoped?
- [ ] Is request validation complete?
- [ ] Is the business lifecycle transition valid?
- [ ] Is the operation transactional where required?
- [ ] Is concurrent execution safe?
- [ ] Is duplicate/replayed processing safe?
- [ ] Are business uniqueness constraints enforced at the database level where appropriate?
- [ ] Are domain events published only after successful commit?
- [ ] Can a consumer safely process the same event twice?
- [ ] Are errors mapped to appropriate API responses?
- [ ] Are tests added or updated?

Before committing a frontend feature:

- [ ] Does it respect the role/workspace model?
- [ ] Does it handle API loading and error states?
- [ ] Does it refresh state after create/update operations?
- [ ] Does it avoid exposing security-sensitive controls solely through UI logic?
- [ ] Does it work with runtime Keycloak configuration?
- [ ] Does the production Angular build succeed?

## 21. Deployment direction

The application is designed to move from Docker Compose development to containerized test/staging and eventually Kubernetes/AWS deployment.

The important principle is to keep the same application/container contracts across environments and externalize environment-specific configuration.

A future production deployment should include, at minimum:

- TLS termination and secure Nginx/ingress configuration.
- Managed or highly available MySQL.
- Managed/high-availability Valkey where required.
- Durable RabbitMQ with monitoring and appropriate retry/DLQ policies.
- Keycloak deployed with production-grade persistence and configuration.
- Secret management.
- Centralized logging and metrics.
- Health/readiness probes.
- Horizontal scaling policies where appropriate.
- Backup and disaster-recovery procedures.
- CI/CD promotion from tested container images.
